# Project context: smokelab

Bibliothèque collaborative de lineups CS2 (pool global par map + profils utilisateurs avec livres personnels et abonnements). Next.js 16 (App Router) + React 19 + TypeScript + Tailwind v4 + Supabase (Postgres + Storage) + iron-session + Steam OpenID.

See [README.md](./README.md) for setup/run instructions and [docs/USER_GUIDE.md](./docs/USER_GUIDE.md) for user-facing behavior.

## Conventions

- UI copy and comments are in **French**; code identifiers are in English.
- Styling is Tailwind utility classes inline, dark theme only (`bg-zinc-950`/`zinc-900` surfaces, `orange-500` accent). No CSS modules, no component library.
- No icon library is installed — icons are hand-written inline SVGs (see `RadarPicker.tsx`).
- Data fetching happens in Server Components; mutations go through Server Actions (`"use server"` files named `actions.ts` colocated with the route, e.g. `src/app/map/[map]/actions.ts`).

## Architecture decisions (non-obvious from code alone)

- **`/` is a marketing/splash landing page, not the app.** The map grid that used to live at `/` moved to `/maps` (`src/app/maps/page.tsx`, unchanged content otherwise) when the cinematic hero landing (`src/app/page.tsx`) was added — full-bleed background, giant animated wordmark, map-name marquee, feature tiles, no `SiteHeader`. Because of this, `SiteHeader`'s logo and the login page's "Continuer sans compte" link point at `/maps`, not `/` — clicking the logo from inside the app should return to the actual library, not bounce back out to the splash. `proxy.ts`'s `GUEST_PATTERNS` allows both `/` and `/maps` for guests. If you add more top-level app routes, decide deliberately whether they belong on the splash's CTAs or only in `SiteHeader`.
- **No Supabase Auth.** Auth is Steam OpenID 2.0 + a custom `iron-session` cookie (`src/lib/session.ts`). Because of this, `auth.uid()` is always `null` in Postgres — any RLS policy referencing it is a fail-safe that blocks the anon key entirely, not a real per-user filter. **All reads/writes must go through `createAdminClient()`** (service role, bypasses RLS) from Server Components/Actions. The anon client exported from `src/lib/supabase.ts` is intentionally unusable for real queries from the browser — don't wire it up to fetch data client-side.
- **`users` table has RLS enabled with zero policies** (see `supabase/schema.sql`) — deliberate, since the anon key is public in the JS bundle and this table holds `steam_id`. Keep it that way; don't add an anon-facing policy without discussing it first.
- **Lineup positions** are normalized `from_x/from_y/to_x/to_y` (0–1, relative to the radar image), set by clicking in `RadarPicker.tsx`. `from_pos`/`to_pos` are separate free-text labels (e.g. "T Spawn") — don't conflate the two.
- **Media uploads** (`media_lineup`/`media_result`/`media_gif`) go to the public Supabase Storage bucket `lineup-media`, created in `supabase/migrations/002_lineup_positions_and_storage.sql`. Field names were reshaped in `003_media_fields.sql` (dropped `media_setup`, renamed `media_aim`→`media_lineup`, added `media_gif`). Uploaded server-side inside the `createLineup` action, never from the client.
- **Schema changes go in `supabase/migrations/NNN_description.sql`**, numbered sequentially (`001_initial_schema.sql` is the base — never edit an already-applied migration, add a new one). Apply with `npm run db:migrate` (wraps `supabase db push --db-url $SUPABASE_DB_URL` from `.env.local`; the CLI tracks applied migrations in `supabase_migrations.schema_migrations`). Migrations applied manually in the SQL Editor before the CLI was set up must be marked with `npx supabase migration repair --status applied <n...> --db-url ...` or `db push` will try to re-run them.
- **`next.config.ts`** sets `experimental.serverActions.bodySizeLimit` to `25mb` (default is 1MB) to allow media uploads through Server Actions — don't remove this without providing another upload path.
- **`RadarPicker.tsx`** uses the browser View Transitions API (`document.startViewTransition`, feature-detected with a graceful fallback) to animate the expand/collapse of the radar into a fullscreen overlay. Zoom is mouse-wheel driven and anchored to the cursor position (not centered); panning is drag-based and only engages past a small movement threshold so a plain click still places a point. If you touch the zoom/pan math, keep the click-vs-drag distinction — it's easy to accidentally break "click to place a point."
- **Map assets** (`public/maps` screenshots, `public/icons` veto emblems, `public/radars` top-down radars) were sourced from community GitHub mirrors of Valve's official CS2 game assets (see git history / prior session for sources), not hand-made — if adding a new map, look for the equivalent asset in the same repos rather than sourcing from elsewhere, to keep filenames/format consistent (`src/lib/mapImages.ts` maps `MapName` → path; some files have a `.png` extension but are actually WebP/JPEG under the hood — verify with `file` before assuming format).
- **Media fields accept image or video** (`accept="image/*,video/*"` in the create form), so anything rendering `media_lineup`/`media_result`/`media_gif` must go through `src/components/MediaView.tsx`, which sniffs the URL extension to pick `<video>` vs `<img>` — never assume these are images and hardcode `<img>`.
- **Three roles: guest / user / admin, but only `users.is_admin` exists in the DB** (added in `004_user_roles.sql`) — "guest" is simply the absence of a session, derived by `roleOf()` in `src/lib/roles.ts`, which also centralizes the permission rules (`can.*`). Guests get read-only access: `proxy.ts` whitelists `/`, `/map/<map>` and `/u/**` via `GUEST_PATTERNS` (mutation pages like `/map/x/new` are deliberately not matched and still redirect to login), and pages must handle `session.user === undefined` instead of redirecting. Server Actions remain the real gate — client-side hiding of buttons is cosmetic. Note `SessionUser.is_admin` is baked into the session cookie at login time (`api/auth/steam/callback/route.ts`), so flipping the DB flag for an existing user requires that user to log out/in again before it takes effect.
- **`lineups.status` gates the map pool** (added in `006_lineup_status.sql`: `personal`/`pending`/`approved`/`rejected` + `rejection_reason`). The map-pool page only queries `status = 'approved'` for its main "Pool" tab. `createLineup` sets `approved` for admins, `personal` for normal users (their lineups live on their profile + books, and the action redirects them to their profile, not the map).
- **Propose/review flow** (`src/app/map/[map]/actions.ts`): `proposeLineup(lineupId)` flips a `personal`/`rejected` lineup owned by the caller to `pending` (button "Proposer au pool" in `LineupDetailModal`, gated by `can.proposeLineup`) and notifies **every** admin (`users.is_admin = true`, queried fresh each time — not cached), not just the one who eventually reviews it. `approveLineup`/`rejectLineup` are admin-only (`can.reviewLineup`, i.e. `role === "admin"`, not a per-lineup owner check since any admin can review any proposal) — approve sets `approved` + clears `rejection_reason`; reject requires a non-empty reason (`RejectLineupDialog`, a small textarea modal) and sets `rejected` + `rejection_reason`. All three notify (proposal -> admins, approve/reject -> the author; see notifications below) and `revalidatePath` both the map and the relevant profile. `MapPoolView` shows a second "Propositions" tab (admin-only, `role === "admin"`) alongside the existing "Pool" tab, backed by a separate `getPendingLineups(map)` query (`status = 'pending'`) fetched only when the viewer is an admin — the radar, type filter, and grid all operate on whichever tab is active (both radar and grid render the exact same merged/deduped list, computed once as `sourceLineups`) except the book-preview picker, which only makes sense on the Pool tab and is hidden on Propositions. `LineupCard`/`LineupDetailModal` show a `StatusBadge` for `pending`/`rejected` (nothing for `personal`/`approved`), and the modal surfaces `rejection_reason` inline to the owner/admin when rejected.
- **Book-scoped lineup creation bypasses admin auto-approval.** `createLineup` normally auto-approves for admins (`can.publishToPool`), but the "+ Créer une lineup" button on a book you own (`/u/[steamId]/books/[bookId]/page.tsx`) links to `/map/{map}/new?bookId={id}`, and `LineupForm` renders a hidden `scoped_to_book` field whenever `scopedBookId` is set. `createLineup` treats that field as an override — `isScopedToBook` forces `publishesToPool = false` regardless of role, so the lineup stays `personal` and lives only in that book, even when the creator is an admin. It still redirects back to the book itself (`/u/{steamId}/books/{bookId}`) rather than the profile, but only if that book is still among the checked `book_ids` at submit time (the multi-select from the previous feature) — if the user unchecked it, it falls back to the profile.
- **Deep-linking a specific lineup on the map page** (`?lineup=<id>` on `/map/[map]`) is how notification links open the exact lineup instead of just the map: `LineupDeepLink` in `MapPoolView.tsx` is a tiny `useSearchParams`-consuming subcomponent (isolated in its own `<Suspense>`, same reason as `ToastFromQuery` in `ToastProvider.tsx`) that looks the id up across both `lineups` and `pendingLineups`, switches `activeTab`/`selectedType` to match, sets `openLineupId`, then strips the param from the URL via `router.replace`. Both `proposeLineup` (link to admins) and `approveLineup` (link to the author) use this; `rejectLineup`'s notification still links to the author's profile instead, since a rejected lineup isn't on the map.
- **Toasts and confirmations**: `ToastProvider` (`useToast()`) and `ConfirmProvider` (`useConfirm()`, promise-based, replaces native `confirm()` — don't reintroduce it) are mounted in the root layout. Server Actions that end in `redirect()` can't toast client-side, so they redirect with `?toast=<code>` and `ToastFromQuery` (inside ToastProvider) maps known codes to messages then strips the param — add new codes to `QUERY_TOASTS` there. The `toast-in` keyframe lives in `globals.css`.
- **`supabase.buckets` writes via raw SQL don't take effect on Supabase hosted** — bucket creation/config must go through the Dashboard or the Storage Management REST API (`POST /storage/v1/bucket`), not a SQL migration `insert`. See the comment in `002_lineup_positions_and_storage.sql`.
- **PostgREST schema cache**: after running a migration's `ALTER TABLE` in the SQL Editor, verify the columns actually exist before assuming code will work — query `GET {SUPABASE_URL}/rest/v1/` (its OpenAPI `definitions.lineups.properties`) with the service role key to see the live schema PostgREST is serving. This caught two migrations that silently never ran in a prior session.
- **Lineup display is split across three components on purpose**: `LineupCard` (dumb thumbnail, takes `onOpen`), `LineupDetailModal` (the big viewer/actions modal, takes `onClose`), and `LineupGrid` (owns which lineup id is open, renders the grid + a single shared modal instance). This exists so a click on a `RadarViewer` marker can open the *same* modal as clicking a grid thumbnail — `LineupGrid`'s `openLineupId`/`onOpenLineupIdChange` props are optional (uncontrolled by default, used standalone on the profile page) but get lifted to `MapPoolView` (map page) and `BookDetailView` (book page) so `RadarViewer` and the grid/selector below share one open-lineup state. Don't reintroduce per-card open state — it breaks that cross-component opening. `LineupGrid` also takes an optional `extraModalLineups` — lineups not rendered as cards but still resolvable if the radar opens their id (used by `MapPoolView`'s book-preview overlay, see below, since a personal lineup on the overlay may not be in the pool grid). `BookLineupSelector` mirrors the same controlled `openLineupId` pattern for the same reason.
- **Books are scoped to one map each, and a user can have several per map** (`books.map`, added in `005_books_and_follows.sql`). There is no cross-map book. `book_lineups` (renamed from `user_lineups`) is a many-to-many between `books` and `lineups`, keyed by `(book_id, lineup_id)` — a lineup can be in several of a user's books at once. The old single-book-per-user "bookmark" concept and its `toggleBookmark` action are gone; membership is managed per-lineup via `BookPicker` (`setLineupBooks`/`getLineupBookIds` in `src/app/u/[steamId]/actions.ts`), which only ever lists/touches books matching *that lineup's* map. The ribbon on `LineupCard` is rendered by the caller (`LineupGrid`/`BookLineupSelector`, as a sibling `LineupBookmarkBadge` absolutely positioned over the card, not inside `LineupCard` itself) from `bookmarks: LineupBookmark[]` (`{ lineupId, bookId, bookName }`, from `getBookmarkedLineupBooks` in `src/lib/books.ts`) — when a lineup is in exactly one of the viewer's books the badge is a real `Link` to that book (`/u/{viewerSteamId}/books/{bookId}`); in several, it links to the first (alphabetically) with a tooltip listing all of them.
- **Profile route is `/u/[steamId]`** (Steam ID, not the internal `users.id` uuid) — same page renders both "my profile" (book creation/deletion, no follow button) and "someone else's profile" (follow button, no book management), branching on `profileUser.id === session.user.id`. `/u/[steamId]/books/[bookId]` is the book-detail route; it also branches: your own book renders the normal `LineupGrid` (per-lineup `BookPicker` still works to move lineups between your books), someone else's book renders `BookLineupSelector` instead — a multi-select grid + "Ajouter à mes livres" (`addLineupsToBooks`) + a "Copier" button per book on the profile (`copyBook`, clones the whole book into a new one you own on the same map). There is no `/my-book` anymore; it was fully replaced by this route. Both branches are wrapped in `BookDetailView` (`src/components/BookDetailView.tsx`), which renders the book's map `RadarViewer` above the grid/selector, plotting every lineup in that book (since a book is always single-map, this needs no map picker) — it owns the shared `selectedType`/`openLineupId` state the same way `MapPoolView` does.
- **Map-page "preview one of my books on the radar" is client-only and per-viewer, not persisted, and affects the grid too.** `MapPoolView` fetches `myBookLineups` (`getUserBookLineupsForMap` in `src/lib/books.ts`, grouped `{ bookId, lineup }[]`, includes the viewer's non-`approved` personal lineups too since those never show up in the pool query) and offers `BookPreviewPicker` — a multi-select checkbox popover (not a native `<select>`, so several books can be shown at once) of the viewer's own books for that map; picking one or more merges their lineups into `sourceLineups`, the single list both the `RadarViewer`'s markers and the `LineupGrid` below render from (deduped by id against the pool) — so a book preview lineup shows up as a real card in the grid too, not just a radar pin. Purely local component state: never touches the DB, invisible to other users looking at the same map page — don't wire it through a server action or query param.
- **Follows** (`follows` table, `follower_id`/`followed_id`) are one-way, no approval — `FollowButton` toggles via `toggleFollow(followedUserId, followedSteamId)`, optimistic client state matching the bookmark/delete pattern elsewhere. Follow/unfollow doesn't gate anything yet (no private profiles) — it's purely informational (follower/following counts on the profile page).
- **`RadarViewer` clusters lineups whose `from_x/from_y` are within `CLUSTER_THRESHOLD` (0.025, normalized 0–1) of each other** into one pin with a count badge. Clicking a pin reveals dashed lines + a clickable landing circle (`to_x/to_y`) per lineup in that cluster; clicking a landing circle calls `onOpenLineup`. Cluster/landing markers call `stopPropagation` on `mousedown` so they don't also trigger the background pan/deselect handler from `useZoomPan`.
- **Radar images are square (1024×1024)** — `RadarViewer`'s and `RadarPicker`'s frames are both `aspect-square` for this reason: `from_x/from_y/to_x/to_y` are stored as a fraction of the image, and any frame with a different aspect ratio would letterbox the image via `object-contain`, making the stored fractions land in the wrong screen position. Don't change either frame to a non-square aspect without accounting for that.
- **There is no `FilterBar` anymore** (removed) — the 4 grenade-type buttons rendered by `RadarViewer` (`selectedType`/`onSelectType`, lifted up to and owned by `MapPoolView`) are the *only* type filter, applied to both the radar and the grid below it so they never disagree. Don't reintroduce a second, separate type filter for the grid — extend `MapPoolView`'s shared state instead.
- **Radar hover-reveal markers need a real hit-box, not just the visible dot.** `RadarViewer`'s landing-cluster markers are wrapped in a sized invisible box (`width`/`height` set explicitly, not just `inset-0` around a tiny button) so the mouse can travel from the base dot to the fanned-out circles above it without leaving the hoverable area — CSS `group-hover` stops the instant the pointer exits the hovered element's actual box, so a hit-box that's smaller than the revealed content is a dead zone. If you add more hover-reveal UI on the radar, size the hoverable wrapper to cover the full reveal, not just the trigger.
- **Radar marker hover-previews (`HoverPreview` in `RadarViewer.tsx`) are gated by JS state (`hoveredId`), not CSS `opacity-0`.** The preview renders `<video autoPlay>` via `MediaView`; a video element starts loading/playing as soon as it's mounted regardless of CSS visibility, so mounting one per marker (there can be many) would preload/autoplay all of them at once. Only the actually-hovered marker's preview is ever in the DOM. **Only landing (`to_x/to_y`) markers ever get a hover preview** — the from-marker (departure point) intentionally has no `hoverHandlers`/preview, only a native `title` tooltip and the click-to-reveal-landing-points behavior. Don't re-add `hoveredId` wiring to the from-marker button.
- **Error handling follows this Next.js version's docs exactly, not the classic pattern**: `createLineup`/`updateLineup` (`src/app/map/[map]/actions.ts`) take `(prevState, formData)` and *return* `{ error: string } | undefined` (type `LineupFormState`) instead of throwing — `LineupForm` drives them through `useActionState`, not a plain `<form action={fn}>`. Every other mutation (`deleteLineup`, `createBook`, `deleteBook`, `copyBook`, `setLineupBooks`, `addLineupsToBooks`, `toggleFollow`) is invoked imperatively from an event handler (not a form), so those still `throw`, and the calling client component wraps the call in try/catch to set a local error-message state instead of letting the exception surface — see `LineupDetailModal`, `BookCard`, `BookPicker`, `FollowButton` for the same shape repeated. Reserve actual uncaught `throw` for things a route-level `error.tsx` should catch (bugs, not user-facing validation).
- **`error.tsx`/`global-error.tsx` use `unstable_retry`, not the classic `reset` prop** — this Next.js version (16.2+) renamed/added it; `reset` still exists but the docs say prefer `unstable_retry`. Don't "fix" this back to `reset` from training-data memory.
- **Notifications** (`notifications` table, `007_notifications.sql` + `008_notification_lineup_proposed.sql` for the `type` check constraint; RLS enabled with zero policies, same reasoning as `users`) are emitted by `proposeLineup` (`lineup_proposed`, fanned out to every admin), `approveLineup` (`lineup_approved`, to the author), and `rejectLineup` (`lineup_rejected`, to the author) — all three in `src/app/map/[map]/actions.ts`. `src/lib/notifications.ts` holds the DB helpers; `getMyNotifications`/`markNotificationsRead` (in `src/app/u/[steamId]/actions.ts`, alongside books/follows since both are "my account" actions) are the two Server Actions a client component can call directly. `NotificationBell` (mounted in `SiteHeader`, logged-in users only) is intentionally self-fetching — it calls `getMyNotifications()` itself in a `useEffect` on mount rather than requiring every page to fetch and thread notifications down as a prop, unlike bookmarks/books elsewhere in this codebase which *are* threaded through Server Components. Opening the dropdown marks everything read in one batch call (`markNotificationsRead`) — there's no per-notification read state. Adding a new `NotificationType` means updating both the TS union in `src/types/index.ts` *and* the DB check constraint via a new migration (see `008_notification_lineup_proposed.sql` for the drop-then-recreate pattern) — the TS type alone doesn't stop a bad insert.

## Known gaps / not yet built

- `book_lineups.mastered`/`note` columns exist but have no UI — adding a lineup to a book only inserts the row, doesn't set these.
- No pagination/infinite scroll on the map pool grid, the "lineups créées" section of a profile, or a book's contents.
- Hover previews only ever appear on landing markers, which are only rendered after a from-marker is clicked (`selectedCluster` set) — there's no way to preview a lineup without a click first, even a from-cluster with a single lineup. Considered acceptable since it matches "hover only ever means landing point," but a future pass could special-case single-item from-clusters to auto-select on hover if this proves annoying.
- No way to rename a book once created, or to remove an individual lineup from *your own* book except by unchecking it in that lineup's own `BookPicker` (no bulk-remove from within your own book view).
- Following someone doesn't surface anything yet (no feed/notifications — the notifications system that exists is lineup-review-only, see above) — it's purely a profile-page count + who-follows-whom fact.
- Notifications have no "delete" or per-item read/unread toggle, and the bell only ever fetches the latest 30 — there's no pagination or "load more."
